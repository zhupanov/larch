# Execution Issues Tracking

**Consumer**: `/implement` call sites that apply OOS triage policy, the `Pre-existing Code Issues` dual-write gate, or file OOS GitHub issues.

**Contract**: Defines the Follow-up Work Principle (three filing paths: inline, OOS GitHub issue, manual `/issue`), the OOS triage policy (four rules governing when to file vs. fold), the file-conflict rule for OOS dependency emission, the `Pre-existing Code Issues` dual-write gate, and the Terminal disposition invariant that governs OOS checkpoint passage. All apply unconditionally on every `/implement` run.

**When to load**: MANDATORY immediately before applying OOS triage policy, the `Pre-existing Code Issues` dual-write gate, or filing OOS GitHub issues. Do not load outside those call sites.

**MANDATORY: READ ENTIRE FILE before composing execution issue descriptions, OOS descriptions, or manual filing prose: `${CLAUDE_PLUGIN_ROOT}/skills/shared/readability-style.md`.**

## Follow-up Work Principle

Durable, actionable follow-up identified during design / implementation / review is tracked through one of three paths, selected by the OOS triage policy below: (a) folded inline into the current PR's commits (no separate GitHub issue), (b) auto-filed via Step 9a.1 as an OOS GitHub issue, or (c) manually filed via `/issue`. The terminal archive's `larch-logs/implement/<RUN_ID>/execution-issues.ndjson` batch is the durable store for execution content for paths (b) and (c). Path (a)'s audit trail is the union of the commit message, the relevant `execution-issues.md` category entry (`Pre-existing Code Issues` for main-agent-discovered defects per the dual-write rule below; `Warnings` for Step 5.5 inline-triage breadcrumbs and for external `oos_observations[]` materialization breadcrumbs; `${CLAUDE_PLUGIN_ROOT}/scripts/larch.sh oos materialize-manifest` runs at Step 2 complete and again at ship pre-trigger, not by prompt-side manifest parsing at Step 9a.1), and, when `$ISSUE_NUMBER` is set, the terminal summary comment which points readers at the archived run log. Filing-path details:

1. **Auto-filed via Step 9a.1** — items fitting the OOS pipeline that survive triage as filed-OOS candidates (accepted OOS from `/design` or Step 5 review voting, or main-agent items via the dual-write below). `${CLAUDE_PLUGIN_ROOT}/scripts/larch.sh oos file` is the Rust-owned filing driver. It composes and caps the batch, plans deterministic conflict edges, creates issues through the typed Rust issue owner, writes filing evidence, and runs the disposition checkpoint. **Design-phase path:** `/design` Step **5b** may already file non-security accepted OOS from `$DESIGN_TMPDIR/oos-accepted-design.md` through the Rust-owned `design file-oos-prepare` / `design file-oos-annotate` workflow and `/larch:issue`. The Rust Step 9a.1 driver treats any `### OOS_` block with a `- **Filed URL**:` field as disposition-satisfied and does not refile it.
2. **Manually filed via `/issue`** — durable follow-up not fitting OOS schema (e.g., a process-level gap surfaced by a warning). After `/issue` returns the number, reference it in the originating `execution-issues.md` entry: append `→ filed as #<N>` to the entry's description line in place. Step 7a checkpoints the entry, and Step 18 appends the final tail before publication.

**Actionability drives filing**, not category. `Pre-existing Code Issues` are always logged in `execution-issues.md` (the durable audit trail) but only dual-write to the OOS artifact when the entry survives triage as a filed-OOS candidate — see the dual-write subsection below for the gate. `Tool Failures` / `CI Issues` / `Warnings` — file when the failure exposes a recurring or systemic defect. Log-only classification is reserved for infrastructure transients such as network, runner provisioning, or quota failures that match no repository test or lint. A named repository test or lint failure is never a one-off: it is either deterministic breakage or nondeterminism, and both are defects in main that the observing run fixes in-branch under the flaky-test doctrine in the SKILL.md Step 8 ci-fixer route. Deviate only when the operator explicitly defers the named failure for this run; record the deferral in the same entry. `External Reviewer Issues` / `Permission Prompts` — typically log-only (operational telemetry); file only when the pattern is persistent across sessions.

**Carve-outs**: Non-accepted OOS (voting rejected) land in the `oos-issues` larch-log batch under the "Rejected / Out-of-Scope Observations (not filed)" sub-block. Compose the record with `jq -nc` — the `-c` flag produces a compact single-line JSON object required by the `json-lines` sanitizer; `jq -n` without `-c` emits multi-line pretty-printed JSON that the sanitizer rejects. Record schema: `{"phase":"<pipeline-phase>","step":"9a.1","category":"OOS","body":"<sanitized-markdown-body>"}` — compose the body first, then pass via `--arg body`. See `docs/run-log-batches.md` § "oos-issues record schema" for the full example. Rejected review findings land in `$IMPLEMENT_TMPDIR/rejected-findings.md` and are written to the `plan-review-tally` / `code-review-tally` batches under dedicated `## Rejected Plan Review Findings` / `## Rejected Code Review Findings` sub-headers — the archived run log is the single source of truth. Step 4 (plan review rejected) and Step 16 (code review rejected) emit only one-line breadcrumbs and do NOT reprint the full findings to the terminal transcript. `repo_unavailable=true` blocks BOTH paths: Step 9a.1 keeps the entry in `oos-accepted-main-agent.md` and reports `Skipped — repo unavailable` in the `oos-issues` batch; manual `/issue` keeps the item in `execution-issues.md` — do NOT call `/issue` manually when `repo_unavailable=true`. **Security findings are NEVER filed via this principle** — route through `${CLAUDE_PLUGIN_ROOT}/docs/security/workflow-trust-and-mutations.md`.

**Sanitize before filing from execution context.** Any issue body or larch-log record composed from execution-session-derived content (execution-issues.md, oos-accepted-main-agent.md, reviewer prose, any session-derived source) MUST apply the dual-write redaction rules below (secrets → `<REDACTED-TOKEN>`, internal URLs → `<INTERNAL-URL>`, PII → `<REDACTED-PII>`) plus the canonical `${CLAUDE_PLUGIN_ROOT}/docs/security/artifacts-redaction-and-publication.md` egress contract. Prompt-level sanitization remains required. The Rust OOS owner applies `larch_core::issue::oos_batch::sanitize_public_text` again before typed issue creation. The separate manual `/issue` path covers secrets at its outbound boundary but not internal hostnames, URLs, or PII. `run-log` applies tmpdir and secret redaction before publishing run payloads.

Log noteworthy issues to `$IMPLEMENT_TMPDIR/execution-issues.md` throughout execution. **Any step** may append. Log pre-existing code issues not fixed, tool failures, permission prompts, external reviewer failures, CI transients, and any uncategorized `⚠` warning.

For tool, Bash, helper, or agent failures where stdout/stderr or a returned error body exists, capture the full content into a step-local file under `$IMPLEMENT_TMPDIR` and append it with:

```bash
[ -z "${CLAUDE_PLUGIN_ROOT:-}" ] && [ -n "${IMPLEMENT_TMPDIR:-}" ] && [ -f "$IMPLEMENT_TMPDIR/plugin-root.env" ] && . "$IMPLEMENT_TMPDIR/plugin-root.env"
"${CLAUDE_PLUGIN_ROOT}/scripts/larch.sh" run-log append-failure \
  --log "$IMPLEMENT_TMPDIR/execution-issues.md" \
  --site "<step-id>" \
  --tool "<tool label>" \
  --exit-code "<exit-code>" \
  --category "<Tool Failures|External Reviewer Issues|CI Issues|Warnings>" \
  --output-file "$IMPLEMENT_TMPDIR/<failure-capture>.log" \
  --redact || true
```

Do not summarize, truncate, or replace the captured body with only an `ERROR=` token. Existing one-line `run-log append-entry` calls remain appropriate for synthetic warnings that do not have tool output, but any real failed invocation must preserve its captured output through `run-log append-failure`.

**Entry format** — entries grouped by category. If the category header exists, insert the bullet at the end of its list; else add header + bullet at EOF.

```markdown
### <Category>
- **Step <N>**: <description with enough detail for later investigation>
```

**Categories** (exact headers; entries chronological within a category; categories not intermixed): `Pre-existing Code Issues`, `Tool Failures`, `Permission Prompts`, `External Reviewer Issues`, `CI Issues`, `Warnings` (for `⚠` not fitting a more specific category; do NOT duplicate), `Q/A` (Step 2 opportunistic questions + mid-coding ambiguity resolutions — see Step 2 for schema and progressive-upsert rule).

## File-conflict rule for OOS dependency emission

**Best-effort when conflict planning succeeds.** Two OOS issues that may run in parallel SHOULD NOT modify the same file unless their Descriptions expose explicit, parseable, non-overlapping line ranges for that file under the inclusive-overlap rule. `${CLAUDE_PLUGIN_ROOT}/scripts/larch.sh oos file` applies the cap and conflict planner in process to `$IMPLEMENT_TMPDIR/oos-combined.md`. `crates/larch-cli/src/oos_file_commands.rs` owns that composition. The standalone `${CLAUDE_PLUGIN_ROOT}/scripts/larch.sh oos issue-cap` and `${CLAUDE_PLUGIN_ROOT}/scripts/larch.sh oos file-conflict-deps` verbs expose the same Rust policy to distinct batch callers such as `/design`. `crates/larch-cli/src/oos_commands.rs` owns those commands. `crates/larch-core/src/issue/oos_batch.rs` owns the cap and parsing, and `crates/larch-core/src/issue/oos_conflict.rs` owns the dependency plan. The deterministic tie-break is lower 1-based batch index blocks higher. The TSV is numeric-only, so sanitization is preserved and no reviewer prose gains a new public surface.

The Rust filer applies the rule only when planning produces a non-empty TSV. It parses those rows into its typed creation order and blocker writes. An empty plan creates no extra intra-batch edge. If conflict-cap validation, conflict parsing, or dependency-file output fails, the filer emits `**⚠ /implement: oos-file-conflict pre-pass failed (exit <N>) — proceeding without caller-supplied serialization edges; review accepted-OOS Descriptions before greenlighting parallel workers**`, appends a `Tool Failures` entry to `$IMPLEMENT_TMPDIR/execution-issues.md`, and continues without deterministic conflict edges. The separate per-run issue cap fails closed before issue creation. The Rust filing path does not invoke `/issue` Phase 2 or an LLM dependency fallback.

**Privacy guardrail.** OOS Descriptions become PUBLIC GitHub issues through the typed Rust issue owner, so reviewer-supplied `path:line` hints become public on filing. Reviewers should follow `${CLAUDE_PLUGIN_ROOT}/docs/security/artifacts-redaction-and-publication.md` and avoid naming high-risk paths or pasting secret-adjacent material in OOS Descriptions. Machine ordering relies on numeric-only edges, so sanitizing prose costs nothing in conflict-detection fidelity.

## OOS triage policy

Before accepting any finding at one of the controlled acceptance points, triage it:

1. Documentation drift (any size): do NOT file an OOS issue. The workflow that detects the drift fixes it as part of the current work (i.e., folded into the current PR). Drift means a stale or now-incorrect doc statement that needs corrective alignment with current behavior — it is identified by what is wrong, not by line count, so rule 1 takes precedence over rule 4 when both could apply (a 40-line doc-drift fix folds inline; it is NOT batched into rule 4).
2. A bug whose fix is < ~30 lines of code: do NOT file an OOS issue. Fold the fix into the current PR.
3. Multiple medium-sized bug fixes (each individually >= ~30 LOC): combine them all into ONE filed OOS issue (not one issue per item).
4. Multiple moderate-sized documentation changes (each individually ~30-100 lines, NOT drift): combine them all into ONE filed OOS issue. Applies to substantive non-drift doc work (e.g., new sections, intentional rewrites of non-stale content) that is genuinely out-of-scope for the current PR.

Threshold convention: rules 2 and 3 use `< ~30` and `>= ~30` respectively, with rule 3 inclusive at the ~30-LOC boundary. The `~` is intentional. The LOC estimate is a natural-language judgment, but the inclusive and exclusive directions at the boundary are fixed. Apply rules 3 and 4 before writing accepted-OOS blocks. The Rust filer may combine related blocks further and then applies the hard per-run cap; it does not decide this upstream LOC triage policy.

**Actionable consequence:** every accepted-OOS artifact entry that survives triage as a filed-OOS candidate MUST either ship as GitHub issue(s) from Step 9a.1 (including combine-to-one URLs), fold into the current PR with explicit `Inline-triage rule N:` commit-body breadcrumbs, or be explicitly rejected into the `oos-issues` log batch. It MUST NOT vanish with no durable disposition. Rules 1-2 do NOT enter accepted-OOS artifacts; fix them inline in the current PR instead. Noteworthy inline fixes that operators may want to audit later, such as a non-trivial pre-existing-code touch outside the user's prompt, should be logged under the `Warnings` category in `$IMPLEMENT_TMPDIR/execution-issues.md` so local checkpoints and the Step 18 terminal tail can append them without filing. For rules 3 and 4, combine each class into one accepted-OOS block before append when more than one item is present. The Rust filer may then combine other related blocks and apply the cap described in `${CLAUDE_PLUGIN_ROOT}/skills/implement/references/oos-pipeline.md`. **Security findings are NEVER folded inline and NEVER filed via this OOS path regardless of size**. Route them through `${CLAUDE_PLUGIN_ROOT}/docs/security/workflow-trust-and-mutations.md` instead. If a finding cannot safely land in the current branch, for example because it would require reverting the core feature, exceed the Step 12d fix budget, or conflict with the accepted plan, file it as a single OOS item even when the small-bug rule would otherwise apply.

**Terminal disposition invariant:** before `OOS_PENDING` clears at the Step 8+ OOS checkpoint, the non-security-routed `### OOS_` blocks aggregated from the accepted-OOS markdown files MUST have verifiable terminal disposition: at least one filed GitHub issue URL recorded for the run (including a combined batch, counted from `oos-issues-created.md`, structured filed-URL fields, or the staged `oos-issues.ndjson`), enough literal `Inline-triage rule N:` substring occurrences in the current branch's commit messages on the gate's `--commit-range` to cover every such block, or enough distinct `OOS_<n>` rejection markers under Rejected sections in the `oos-issues` log batch. The inline and rejection counters are aggregate heuristics, not per-block links. Silent drop (accepted blocks present, zero URLs, insufficient inline breadcrumbs, and insufficient rejected markers) is forbidden. See NEVER #14–15 and `${CLAUDE_PLUGIN_ROOT}/scripts/larch.sh oos disposition-gate`. **Strict URL gate (Step 8+):** the Rust gate counts only disposition evidence from its declared inputs: structured `- **Filed URL**:` lines in accepted-OOS bodies where applicable, URL tables in `oos-issues-created.md`, `--filed-urls-file` paths, and the NDJSON batch. It does not count incidental GitHub links pasted only inside a filed issue's Description or other prose outside those mechanical surfaces.

## Mechanical enforcement: `Pre-existing Code Issues` dual-write

Whenever the main agent identifies a Pre-existing code issue, log it under `Pre-existing Code Issues` in `execution-issues.md` regardless of triage outcome (the log is the durable audit trail). Then apply the OOS triage policy above: if and only if the item survives triage as a filed-OOS candidate (i.e. NOT doc drift and NOT a < ~30 LOC bug), the agent MUST also append a corresponding `### OOS_N:` block to `$IMPLEMENT_TMPDIR/oos-accepted-main-agent.md` so Step 9a.1 can file it. External implementer `oos_observations[]` are materialized by `${CLAUDE_PLUGIN_ROOT}/scripts/larch.sh oos materialize-manifest` at Step 2 complete and again at ship pre-trigger. `crates/larch-cli/src/oos_commands.rs` owns that Rust command, `crates/larch-core/src/issue/oos_batch.rs` owns its composition and security-routing rules, and their Rust unit tests are the behavioral authority. Step 9a.1 does not parse manifest JSON in prompt-side prose. Items classified by triage as "fold inline" are logged under `Pre-existing Code Issues` but are NOT dual-written to the OOS artifact; the inline fix lands in the current PR's commits. This dual-write rule is mechanical, runs in every mode, and converges main-agent-discovered bugs into the same accepted-OOS pipeline as reviewer-surfaced OOS from `/design` and Step 5. For durable follow-up outside this category, enforcement is prescriptive (principle above), not mechanical; use `/issue` directly.

**Schema** (matches `larch_core::issue::parse_issue_input` and the Rust `"${CLAUDE_PLUGIN_ROOT}/scripts/larch.sh" issue parse-input` command):

```markdown
### OOS_<N>: <short title — one line>
- **Description**: <file path and line number(s)>; <what is wrong>; <concrete reproduction context>; <suggested fix — one or more options>. May span multiple non-blank lines.
- **Reviewer**: Main agent
- **Vote tally**: N/A — auto-filed per policy
- **Phase**: implement
```

`<N>` is a per-session sequential index from 1. To correct an existing entry, use **in-place replacement**: locate by `<N>` and overwrite, preserving `<N>`. Do NOT append on correction (duplicates). The dedup guard below applies only to **new** entries: scan for a block whose title matches case-insensitively after whitespace stripping; if matched, do NOT append. The Rust filer reuses persisted stable IDs, filed URLs, and normalized-title matches across retries. It does not invoke `/issue`'s LLM dedup pass.

**Sanitize the description before append.** Redact secrets / API keys / OAuth / JWT / passwords / certificates → `<REDACTED-TOKEN>`; internal hostnames / URLs / private IPs → `<INTERNAL-URL>`; PII (emails, names, account IDs linked to a real user) → `<REDACTED-PII>`. The Description is forwarded verbatim into a public GitHub issue — paraphrase reproduction context rather than copying log lines when in doubt.

If `oos-accepted-main-agent.md` does not exist, create it with the new entry. If `repo_unavailable=true`, still append (Step 9a.1 skips filing). **Repo-unavailable audit-loss disclosure**: in `repo_unavailable=true` mode, neither tracking-issue summary comments nor the PR body's Execution Issues block exist (Phase 3 slim PR body dropped the Execution Issues block, and without repo access no summary comments can be created). `$IMPLEMENT_TMPDIR/execution-issues.md` is the only audit trail and is removed at Step 18. Operators running with `repo_unavailable=true` must preserve the tmpdir manually if an audit trail is required.
